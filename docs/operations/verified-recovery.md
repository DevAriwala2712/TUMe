# Verified recovery on a disposable Linux device

T3.1 and T3.2 provide one local, operator-approved procedure for `tume-recovery-demo.service`. This service is a noncritical fixture installed separately from the health watcher. The approval flow and executor work offline without an LLM. Keep this procedure on a disposable host until the release gate is met.

## Trust boundary

`nanoclaw-next recovery preview tume-recovery-demo.service` describes revision 1 and makes no state changes. The only executable action lives in the separate Linux `tume-recovery-executor`. It uses a fixed canonical systemd unit and an exact root-owned registry marker. The unit must come from `/etc/systemd/system/tume-recovery-demo.service` without drop-ins or pending manager reload. It must be failed or inactive with no main process or queued job when execution starts.

Install the helper as an ordinary root-owned binary at `/usr/local/libexec/tume-recovery-executor` with mode `0755`. The sample sudoers policy grants that exact binary to the dedicated local group `tume-recovery-operators`, with a terminal, fresh password authentication, and environment overrides disabled. The helper also recognizes direct root execution. Under sudo it binds the request to the UID generated by sudo and checks that the launching process is the expected sudo executable. Treat group membership, sudo configuration, the helper and the demo unit as administrator-managed policy. Keep broader sudo privileges and shell access outside this operator role.

Approval requires the operator to type a fresh challenge into the controlling terminal after reviewing the procedure. The stored approval binds that principal, machine identity, boot identity, procedure revision, and exact typed target to a random identifier. The identifier expires five minutes after approval using the Linux boot clock. Copying an approval ID grants no rights to a different operator or device. A changed boot invalidates pending approvals. Log text, findings, model output and the preview CLI have no access to this authorization path.

## Install on an authorized disposable host

Use Linux systemd, a local ext4 state directory, a unique initialized `/etc/machine-id`, sudo and Python 3 for the demo fixture. Build Zig 0.15.2 with `zig build -Doptimize=ReleaseSmall` on Linux and use the `tume-recovery-executor` built for the host. Install from a trusted checkout as an administrator.

1. Create `/usr/local/libexec` as root with mode `0755` and `/var/lib/tume-recovery` as root with mode `0700`. State directory ancestors must be root-owned, have no symlinks, and be writable only by root.
2. Install `tume-recovery-executor` in `/usr/local/libexec` with mode `0755`. Install [the demo server](../../deploy/recovery/tume-recovery-demo.py) in the same directory with mode `0644`. Install [the demo unit](../../deploy/systemd/tume-recovery-demo.service) in `/etc/systemd/system` with mode `0644`, then run `systemctl daemon-reload`. Leave the service disabled at boot.
3. Create the system group `tume-recovery-operators`, grant membership to selected operators, and validate [the sudoers example](../../deploy/recovery/tume-recovery.sudoers) with `visudo -cf PATH`. Install it as root with mode `0440` at `/etc/sudoers.d/tume-recovery`, then run `visudo -c`. Require a new login for changed group membership.
4. Install [the exact registry marker](../../deploy/recovery/policy.example) as root with mode `0600` at `/var/lib/tume-recovery/policy`. Absence disables approval and execution. To change policy or the registered unit while the helper is installed, hold an exclusive `flock` on `/var/lib/tume-recovery/.executor.lock` during the change. Preserve the lock inode. If creating it before the first helper use, create it as root with mode `0600`.

## Approve, execute and inspect

```sh
nanoclaw-next recovery preview tume-recovery-demo.service
sudo /usr/local/libexec/tume-recovery-executor approve tume-recovery-demo.service
sudo /usr/local/libexec/tume-recovery-executor execute APPROVAL_ID
sudo /usr/local/libexec/tume-recovery-executor audit
```

Use the ID printed after approval. One approval can authorize one restart. The helper serializes work per target and reserves audit capacity before writing a durable intent. It rechecks the service after the durable write and uses systemd's fail job mode for dispatch. An administrator acting directly through systemd can still change the target between the last check and the restart request. The audit records approval, intent, the observed dispatch result, and the independently checked service and functional outcome. A successful outcome requires an active canonical service, a stable systemd invocation, and an exact socket response from its main process. TUMe allows zero automatic retries. Rollback eligibility is false for this revision.

| Exit status | Meaning |
|---|---|
| 0 | Approval recorded, audit printed, or service and function verified |
| 2 | Invalid arguments |
| 3 | Refusal or operational error, including a disabled procedure, expired token, target lock contention or full audit |
| 4 | Ambiguous outcome or an attempt requiring reconciliation |
| 5 | Independently observed health failed verification; escalate to the operator |

If dispatch or outcome persistence is interrupted, inspect the audit and local systemd job/journal. A supervisor retains the same target lock until the in-flight systemctl child exits. After there is no pending job, the original operator or direct root can explicitly reconcile.

```sh
systemctl show --property=Job,ActiveState,InvocationID tume-recovery-demo.service
journalctl --unit=tume-recovery-demo.service
sudo /usr/local/libexec/tume-recovery-executor reconcile APPROVAL_ID
```

Reconciliation checks current service and functional health, records who performed it, and never issues a restart. A verified reconciliation establishes the current state. The cause or historical dispatch result can remain unknown. If the target is still in transition or state cannot be read, keep the attempt unresolved and escalate.

The private audit holds at most 64 events and 64 KiB. Each publication uses a synced file, atomic replacement and directory sync on ext4. Errors fail closed. When full, follow the audit rotation procedure below. Never rotate an unresolved audit or remove the live lock inode. Retain the original audit privately on removal because it contains local device and user identifiers. To remove the installation, revoke sudo access, disable policy under the lock, stop and remove the demo service, reload systemd and remove the helper and Python file. Preserve unresolved audit evidence for manual follow-up.

## Disposable acceptance trial

The [trial harness](../../deploy/recovery/run-disposable-trial.py) uses a fresh authorized VM, creates a disposable password-authenticated operator, and stages the exact fixture and policy above. It leaves them installed for inspection. Invoke it as VM root with `--disposable-vm PATH_TO_NANOCLAW_NEXT PATH_TO_EXECUTOR`. It checks a successful restart, a systemctl exit-zero restart with a failed functional probe, and a crash during dispatch followed by explicit reconciliation without another invocation. Keep sanitized results and report host, systemd version, whole-system overhead and operator workload before proposing a product release.

## Opt in to guarded recovery for one boot

The automatic path applies only to the same disposable demo after the manual trial. It requires a separately installed root-only `tume-recovery-automatic` executable at `/usr/local/libexec/tume-recovery-automatic` with mode `0755`. It takes no arguments, and the manual sudo policy does not grant it. It will consider only an explicitly failed service with no queued job or outstanding manual approval. Automatic recovery sends a start request for a failed unit. An already active unit remains running. Stop automation before making direct systemd changes to the target, and keep other controllers and dependencies from starting or stopping the demo during the window. The final service check and the systemd request are separate operations. A new boot invalidates the window. At most one automatic attempt is permitted on each boot, and failed or interrupted verification opens the circuit across boots.

1. As root, create a private `automatic-policy` file in `/var/lib/tume-recovery` by atomic rename from a root-owned mode `0600` temporary file in the same directory. Keep the existing `policy` file installed. Use the exact registry line below followed by this boot's 32 lowercase hex digits and decimal start/end times in Linux BOOTTIME milliseconds. The end is exclusive and at most 120000 ms after the start.
2. Confirm the service is still disposable and the `automatic-stop` entry is absent. The switch and policy are rechecked after durable intent and again in the dispatch child.
3. Invoke the root binary directly or install the [oneshot unit](../../deploy/systemd/tume-recovery-automatic.service) and [timer](../../deploy/systemd/tume-recovery-automatic.timer). Run `systemctl daemon-reload` after installing either unit. The timer has no boot enablement target. A root operator can start it for this boot with `systemctl start tume-recovery-automatic.timer` and should stop it after the window with `systemctl stop tume-recovery-automatic.timer`.

```text
enable restart-demo revision 1 tume-recovery-demo.service
CURRENT_BOOT_ID START_BOOT_MS END_BOOT_MS
```

Read the boot ID from `/proc/sys/kernel/random/boot_id` and remove the hyphens. For the current boot clock in milliseconds use `python3 -c 'import time; print(time.clock_gettime_ns(time.CLOCK_BOOTTIME) // 1000000)'`. The automatic entry exits successfully without dispatch when its policy or window is closed, the service is ineligible, a manual approval has priority, or the boot allowance is spent. It reports the reason on stderr. Circuit, audit and unresolved-result errors remain visible as nonzero status.

To revoke a window, create `/var/lib/tume-recovery/automatic-stop` immediately, stop the timer if active, and remove `automatic-policy`. The switch's presence blocks new dispatches, including a pending attempt that reaches the final policy check after revocation. A start request already accepted by systemd may finish. Keep the switch in place while handling an incident. For an ambiguous automatic attempt, direct root follows the reconciliation flow. The ID is printed by the automatic entry when available and can be recovered as the hexadecimal form of the pending event's 16-byte JSON `id` array.

For a full audit or a latched circuit, keep automation stopped, remove the old window, and review the failure. Resolve any pending attempt with the read-only reconciliation before rotating. Rotate after a subsequent boot and only when the current boot has no automatic intent in the ledger. With the registry disabled and the same exclusive lock held, archive `audit.json` to protected local storage, remove the current audit, and retain the lock inode. A future automatic attempt requires a newly reviewed window. Manual recovery is still available after reconciliation and fresh approval.

The [guarded trial](../../deploy/recovery/run-guarded-trial.py) runs after the manual trial on the same authorized VM and leaves the timer inactive, deletes the trial window and sets the stop switch. Real-device rollout and the operator/workload comparison remain pending.
