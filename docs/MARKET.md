# TUMe market and application review

Reviewed 2026-11-07 against product documentation and upstream project material. The capabilities below are documented offerings. Their resource cost, reliability and operator experience have yet to be compared on TUMe's target hardware. See the [feature roadmap](PLAN.md) for proposed TUMe work and acceptance gates.

## Applications and services available today

| Application or service | What others provide | TUMe decision |
|---|---|---|
| Local service supervision | Monit checks processes, filesystems, programs and network endpoints. It can notify, restart a service and stop restarting after a configured limit. systemd already has restart policies and watchdog support. [Monit manual](https://mmonit.com/monit/documentation/monit.html) · [systemd service reference](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) | **T1/T3.** Compare T1 to Monit. Use systemd as the supervisor. Build only the evidence, approval and independent verification needed for a procedure that systemd restart alone cannot cover. |
| Edge and infrastructure monitoring | Netdata documents collectors, local alert evaluation and fleet aggregation on a Parent, including ARM edge deployments. Zabbix proxies collect remotely and buffer data for intermittent connections. [Netdata edge monitoring](https://learn.netdata.cloud/docs/edge-device-monitoring) · [Netdata alerting](https://learn.netdata.cloud/docs/alerts-%26-notifications/) · [Zabbix proxies](https://www.zabbix.com/documentation/current/en/manual/concepts/proxy/distributed_monitoring) | **T1/T5/T6.** Use Netdata as an edge benchmark. Build a small local evidence set and a bounded outbox if pilot sites need it. Connect to an existing monitoring stack when broader metrics are needed. |
| Dashboards, telemetry pipelines and alert routing | Prometheus Node Exporter exposes hardware and OS metrics. Alertmanager groups, silences, inhibits and routes alerts. Grafana Alloy collects Prometheus and OpenTelemetry signals. [Node Exporter](https://github.com/prometheus/node_exporter) · [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/) · [Grafana Alloy](https://grafana.com/docs/grafana-cloud/send-data/alloy/introduction/otel_alloy/) | **T4/T5.** Export a low-cardinality metrics set and versioned findings. Delegate general dashboarding, telemetry processing and alert routing to existing tools. |
| Uptime, certificates and job heartbeats | Uptime Kuma provides HTTP, TCP, DNS and other checks with status pages. Prometheus Blackbox Exporter probes endpoints. Healthchecks.io detects missing scheduled job pings after a grace period. [Uptime Kuma](https://github.com/louislam/uptime-kuma) · [Blackbox Exporter](https://github.com/prometheus/blackbox_exporter) · [Healthchecks.io](https://healthchecks.io/docs/monitoring_cron_jobs/) | **T5/T6.** Add bounded local functional probes and optional heartbeat forwarding. Correlate internal failure with external reachability. Use an external observer to distinguish silence from a healthy device. |
| AI-assisted troubleshooting | Datadog Bits investigates with metrics, logs, traces and other evidence. It can return a conclusion, next steps or an inconclusive result. [Datadog Bits Investigation](https://docs.datadoghq.com/bits_ai/bits_investigation/investigate_issues/) | **T2.** Build local, on-demand explanation over bounded evidence. Measure correct and inconclusive results and include the resource cost of a correct answer. Keep deterministic next checks available. |
| On-call response and automation | PagerDuty provides alert grouping and actions backed by runbook runners. Event-Driven Ansible connects event sources and conditions to playbooks or modules. [PagerDuty automation](https://docs.pagerduty.com/ai-automation/automation/automation-actions) · [Ansible rulebooks](https://docs.ansible.com/projects/rulebook/en/latest/introduction.html) | **T3/T5.** Build a small locally authorized procedure registry and auditable outcomes. Send structured incident notifications to existing on-call tools. Keep inbound messaging and third-party playbook execution out of the first release. |
| Endpoint security and posture | Falco emits rule-triggered runtime alerts as JSON. Wazuh includes file integrity monitoring, vulnerability inventory and active response. [Falco output channels](https://falco.org/docs/concepts/outputs/channels/) · [Wazuh integrity monitoring](https://documentation.wazuh.com/current/getting-started/use-cases/file-integrity.html) · [Wazuh vulnerability detection](https://documentation.wazuh.com/current/user-manual/capabilities/vulnerability-detection/how-it-works.html) · [Wazuh Active Response](https://documentation.wazuh.com/current/user-manual/capabilities/active-response/index.html) | **T5.** Import one alert format first, preserve source and rule, and explain what was observed. Leave detection, blocking, quarantine and scanning to established tools. |
| IoT release delivery and device management | Mender models deployments and supports OS updates with rollback on integrated devices. balenaCloud provides device logs and release pinning. Portainer's Edge Agent supports management through device-initiated connectivity. [Mender deployments](https://docs.mender.io/overview/deployment) · [Mender OS rollback](https://docs.mender.io/get-started/deploy-an-operating-system-update) · [balena logs](https://docs.balena.io/learn/manage/device-logs) · [balena releases](https://docs.balena.io/reference/api/resources/fleet) · [Portainer Edge Agent](https://docs.portainer.io/advanced/edge-agent) | **T5/T6.** Start with release and update visibility plus pre/post health evidence. Use vendor APIs for delivery, rollback and container management. |
| Offline IoT fleet infrastructure | AWS IoT Core documents device provisioning. Greengrass provides local components and state shadows. Azure IoT Edge documents offline operation and bounded storage of messages for replay after reconnection. [AWS provisioning](https://docs.aws.amazon.com/iot/latest/developerguide/iot-provision.html) · [Greengrass components](https://docs.aws.amazon.com/greengrass/v2/developerguide/ipc-local-deployments-components.html) · [Greengrass shadows](https://docs.aws.amazon.com/greengrass/v2/developerguide/interact-with-shadows.html) · [Azure offline operation](https://learn.microsoft.com/en-us/azure/iot-edge/offline-capabilities) | **T6.** Build only the device identity and synchronization needed for TUMe findings. Prefer the customer's existing fleet transport when it meets offline, identity and data-ownership requirements. |
| Remote support and managed endpoints | NinjaOne documents endpoint monitoring, automation and patching capabilities with platform-dependent coverage. Tailscale SSH provides policy-controlled access to hosts. [NinjaOne RMM](https://www.ninjaone.com/rmm/) · [NinjaOne Remote for Linux](https://www.ninjaone.com/docs/remote-and-quick-connect/remote-troubleshooting/linux-remote-devices/) · [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh) | **T4/T6.** Offer redacted evidence bundles and handoffs to approved support tools. Keep unrestricted remote terminal, patch inventory and access networking with existing products. |
| Hardware health and power | smartmontools queries and monitors supported storage devices. Network UPS Tools exposes UPS status to clients. [smartmontools](https://www.smartmontools.org/static/doxygen/) · [Network UPS Tools](https://networkupstools.org/docs/user-manual.chunked/Overview.html) | **T5.** Add one hardware adapter only after a pilot identifies a failure mode and the required read access fits the budget. Keep firmware updates and power control outside that adapter. |
| Local AI serving | llama.cpp provides an inference server. Ollama offers controls for how long models stay loaded and for request queuing. [llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) · [Ollama FAQ](https://docs.ollama.com/faq) | **T2.** Start with a bounded adapter to a preinstalled backend. Compare resident serving only when operator demand and full-footprint measurements justify it. Retain lineage for any reused scheduler or estimates. |

## Potential deployments

| Deployment | Protected workload and failure to test | Candidate package | Priority |
|---|---|---|---|
| Small Linux gateways and remote sensors | MQTT broker or forwarder runs out of disk, stalls on memory, loses a dependency or spends hours offline | Local checks, offline status, incident replay, one verified service recovery, optional site heartbeat | **First pilot.** Matches the Linux edge scope and supplies a workload with measurable latency and delivery. |
| Digital signage and kiosks | Player process is alive but playback or heartbeat has stopped. Disk is full or an update regressed playback. | Local functional probe, evidence export, release health and operator-approved recovery | **Second pilot candidate.** Validate playback separately from process state. |
| Small-server and homelab operators | Backups stop, certs expire, disks fill or a container reports unhealthy | Service and backup checks, bounded notifications, read-only support bundle | **Adapter candidate.** Check what would be easier with the operator's existing Monit, Uptime Kuma or Grafana setup. |
| Remote lab and environmental stations | Power interruption, SD/storage degradation, backhaul loss, delayed data upload | UPS/storage inputs and offline reconciliation, then grouped fleet views | **Later pilot.** Confirm hardware access and local queue behavior before adding power control. |
| Managed edge providers | Support teams need evidence, tenant boundaries and rollout status across customer sites | Enrolled fleet, site groups, health gates, incident routing and delegated support access | **Later pilot.** Requires identity, revocation, tenancy, delivery and isolation evidence. |

Potential service offers are a single-device deployment guide, a paid or unpaid pilot with a published resource report, optional health-profile onboarding, and later fleet health reporting for managed operators. These are proposed forms of delivery. Validate what operators would adopt through pilot interviews, supported environments, installation time, diagnosis time and repeat incident outcomes before making packaging or commercial commitments.

## Product hypothesis to test

An offline operator can move from a trustworthy observation to a verified recovery for a common gateway fault without disrupting the protected workload. Test three separate outcomes against the same scenario and observation window: alert correctness and latency against Monit or Netdata, diagnosis usefulness against deterministic next checks, and verified recovery against manual/systemd-only handling. Track operator time, misses, false alarms, failed actions and the complete on-device footprint. Compare each baseline under the same target workload and publish the settings and trade-offs.
