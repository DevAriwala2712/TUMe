# T2.2 Diagnostic admission and isolation

TUMe runs an on-demand local explanation in a dedicated Linux cgroup v2 leaf. The operator provisions a memory limit, zero swap, a finite CPU quota, and a finite task limit. The CLI admits one job at a time across the hierarchy, keeps observation independent of the job, and starts the trusted preinstalled adapter in the leaf with a fixed environment and only the standard streams. A private start gate keeps the forked child from executing the backend before successful attachment.

Live host and ancestor readings are mandatory. Reserve the full leaf memory cap on the host and every finite ancestor memory boundary before starting. Reject jobs whose configured measured peak does not fit in the leaf. During execution, sample host memory and CPU/memory PSI, and verify that host and ancestor headroom still cover the reserve plus remaining growth to the cap. On pressure, cancellation, timeout or a capture error, kill the leaf recursively and confirm it is empty. Return an explicit cleanup failure if the kernel does not confirm cleanup in a bounded interval.

The backend contract uses direct arguments including a token cap supplied by the explanation adapter. The runner limits argument and combined stdout/stderr bytes independently. Only stdout from a completed job reaches the explanation parser. The broker uses fresh measurements instead of inheriting the research scheduler's best-effort measurement defaults. T1 continues to produce findings and T2.1 continues to offer deterministic checks when admission fails.

An in-process backend would couple inference failure with monitoring. Moving a running child after exec leaves a race before isolation. A pre-created leaf with gated attachment and recursive kernel kill supports limits and descendant cleanup without a persistent inference service. A native trial reproduced a kernel bug in the original atomic creation approach. The start gate keeps the backend blocked throughout attachment. The selected design requires a trusted local adapter and a host-native deployment. Fixtures exercise admission and lifecycle decisions. Kernel behavior and whole-device impact require separately authorized Linux trials.
